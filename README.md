# metaLogger

The metaLogger project is for adding logging instances to remote machines with the intention of logging data to the meta Logger service on `theAxeRant.com`

## New Logging Deployments

### Requirements
* php >= 7.2

### Install the phar file

The phar file can be downloaded from the [releases][1] section of the project.  The phar file can be copied to the 
intended server and run from there. 

```bash
wget https://github.com/theAxeRant/metaLogger/raw/refs/heads/main/release/metaLogger.phar
```

### Create the config file

An api auth_key needs to be generated on theAxeRant.com server for the intended user who is doing the logging.

An empty configuration file can be generated by running 
```shell
php metaLogger.phar config:create --config=<filename>
```

### loggers

The metaLogger has several loggers capable of reporting different things to the meta logger service.

#### ip check

The IP check reports local IPv4 addresses. Parser versions `1`–`3` use `ifconfig`; version `4` uses `ip a` for systems such as Debian 13. Version `4` requires `iproute2` (`apt install iproute2` on Debian), excludes loopback and IPv6 addresses, and removes CIDR suffixes. Set the expected network mask to filter out other interfaces, including Docker bridges. Multiple matching addresses are reported on separate lines.

Select version `4` in your configuration (or when prompted by `config:build`):

```yaml
log:
  ip:
    version: 4
    mask: 192.168.1.0/24 # replace with your local network
```

#### drive

The `drive` key can contain a collection of named paths.  The paths are passed to the php `disk_free_space()` function, this will report the free space on the coorepsonding filesystem or disk partition.  This value will be reported in MB with the probided name as the key.

```yaml
file_access:
    - {name: "", path: "" }
```

#### file_access

The `file_access` key can contain a collection of named paths.  The paths should be to individual files, but directories are acceptable as well.  The script will report the last file access time of the path provided with the name as a key.

```yaml
file_access:
    - {name: "", path: "" }
```

#### file_count

The `file_count` key can contain a collection of named paths.  The paths are used to `glob` a filecount and report that count using the name as a key.

```yaml
file_count:
    - {name: "", path: "" }
```

### Setup the crontab job

Full paths should be used when creating cronjobs, this is an example of a metaLogger implementation on a raspberry pi.  Note the full path for the php command, metaLogger.phar and the configuration file to be used.

```crontab
*/5 * * * * /usr/bin/php /home/pi/services/metaLogger/metaLogger.phar config:run /home/pi/services/metaLogger/config.yaml
```

## Development of metaLogger

Development and PHAR packaging use Docker Compose. Copy
`devops/dev/compose.override.yaml.example` to `devops/dev/compose.override.yaml`
and replace `<path to solution>` with the absolute path to this checkout.

Run these commands from the repository root:

```sh
make build # build the PHP development image
make up    # start development containers
make bash  # start containers and open an interactive PHP container shell
make down  # stop development containers
make phar  # build the image, install dependencies, and package the release
```

Running `make` without a target also runs `phar`. The PHAR workflow installs
dependencies from `symfony/composer.lock`, builds `symfony/metaLogger.phar`, and
copies it to `release/metaLogger.phar` using Docker Compose. A release-directory
mount is optional. The workflow stops the development containers on completion
or failure and returns a failing status if any build, copy, or cleanup step fails.

Inside the PHP container, `make build` from `symfony/` only builds the PHAR;
the root Makefile handles copying it into `release/` and stopping containers.

### Automatic PHAR builds

The **Build PHAR** GitHub Actions workflow runs on pushes to repository branches.
It tests the code with PHP 7.2, builds with pinned Composer and Box versions, and
checks that the packaged application files match the source. The version comes
directly from `Application::VERSION`; update that constant when changing the
declared release version. The workflow adds no version suffix and does not bump
the version automatically.

After verification, a separate job commits only `release/metaLogger.phar` back
to the same branch using `github-actions[bot]`. Builds whose branch has advanced
are discarded, and newer pushes start a replacement build. Every branch push
triggers a build so even a documentation-only push can replace an older run.
The bot's own push uses `GITHUB_TOKEN`, which does not trigger another push
workflow. Tests run before the bot commit; that commit does not start other
push-triggered CI workflows either.

The publishing job needs `contents: write` permission. Repository or organization
policies and branch protections must permit its ordinary push; the workflow does
not bypass those rules. Pull requests from forks do not trigger publication in
this repository. To rebuild manually, select **Actions > Build PHAR > Run
workflow** and choose a branch. Workflow files must be committed and pushed
before the automation can run; manual dispatch also requires the workflow on
the repository's default branch.

### Workflow security checks

The **Workflow security** workflow runs zizmor on pushes, pull requests, and
manual dispatches. It scans all workflows for unsafe patterns and requires
actions to be pinned to full commit hashes. Online audits also check action
references against GitHub's current security information. Both the zizmor
action and its CLI version are pinned.

Findings fail the check directly, without requiring GitHub Advanced Security
or repository write permissions. To enforce this check before merging, make
`zizmor` a required status check in the applicable branch rules.

### Debian 13 IP parser tests

With Composer dependencies installed in `symfony/vendor/`, run from the repository root:

```sh
docker build -f devops/images/debian13-test.Dockerfile -t metalogger-debian13-test .
docker run --rm -v "$PWD/symfony:/app:ro" metalogger-debian13-test
```

This runs the PHPUnit suite using Debian's PHP and PHPUnit packages, including a live version `4` check against the container's network interfaces without `ifconfig`. Fixture tests cover loopback/IPv6 exclusion, CIDR removal, multiple interfaces, network-mask filtering, and empty results. The live container test is skipped outside this image.
